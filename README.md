# drive-replay

Replay recorded drives through an ADAS stack on x86, and turn that into three everyday tools:

1. **One run command.** `replay run scene-0061` resolves the recording (verified by sha256), the build drop,
   the layered config, the time window and the pre-roll by itself, runs the stack and judges the result.
2. **Bug replay.** `replay bug BUG-0002` reproduces a reported issue straight from its recording on the drop it
   was reported against, checks that the window replay matches the whole-drive replay, and proves the fix on a
   newer drop, including the whole recording.
3. **Replay CI.** Every build drop replays the full suite and gets a PASS / FAIL verdict: runs, deterministic,
   requirements (ground-truth oracle) and regression (golden baselines). A FAIL blocks the merge.

The stack under test is small but real: a radar forward collision warning in C++17 (radar frontend,
clustering, Hungarian assignment, Kalman tracker, path prediction, warning state machine). The recordings are
real drives: 10 nuScenes v1.0-mini scenes with the front radar, converted to MCAP, plus 3 must-warn cases
with an injected target. Everything builds with **Bazel** (C++ and Python, hermetic Python toolchain).

Demo: https://huggingface.co/spaces/pavanyadava07/drive-replay - Results: [docs/RESULTS.md](docs/RESULTS.md)

## What the tooling found

The three bugs, the window-fidelity problem and the silent-stack problem came out of the suite while the stack was being written. The silent regression is a deliberate demo:

| | found by | what happened |
|---|---|---|
| BUG-0001 | replay suite on v0.1.0 | warnings on oncoming cars on a bending road (scene-0103) |
| BUG-0002 | replay suite on v0.1.0 | warning on a construction worker beside the path in a left turn (scene-0061) |
| BUG-0003 | **CI on the fix for 0001/0002** | the new curved corridor kept "turning" at the exit of a bend and warned on parked cars in two recordings the tickets never touched (scene-0916, scene-1094). Both focused bug replays had passed. The suite failed that release candidate (run locally with the same `replay ci` command CI uses). |
| silent regression (demo) | CI on draft PR #1 | a one-line "less flicker" tweak (debounce 2 -> 4 cycles). The FCW unit tests were first changed to read the debounce from `Params`, as a developer making this change on purpose would do. Unit tests pass, the oracle's requirements pass, and only the golden comparison shows every warning arriving 0.15 s later. |
| window fidelity | building `replay bug` | a bug window replayed without pre-roll still "reproduced", but 0.22 s later and with a different TTC, because the tracker starts cold. `replay bug` now compares the window against the whole-drive replay and says when they diverge. Measured: 0.25 s of pre-roll is enough in these cases, but **not monotonic**: 1.0 s diverged in one case where 0.5 s and 2 s did not. |
| a stack that never warns | reviewing v0.2.0 | v0.2.0 passed every requirement with zero warnings, because the mini drives contain no real forward-collision threat. The suite now has 3 injected must-warn cases, so a silent stack fails. |

All numbers: [docs/RESULTS.md](docs/RESULTS.md), generated by `scripts/reproduce.py`.
On GitHub the workflow is green on `main`, and draft PR #1 (the debounce tweak) is blocked by exactly the three
regressions listed above; the Ubuntu runner, with its own CPU and compiler, reproduces the golden events accepted on
the development machine.

Headline (AMD EPYC 7R13): the whole 13-recording suite, each replayed twice, takes about 1 s; one core replays
at about 120x real time, 32 parallel jobs at about 1,650x; every recording gave the same digest in all 10 repeats.

## Quick start

```bash
bazel test //...                                     # 5 C++ GoogleTest targets + 4 Python pytest targets
pip install -r tools/convert/requirements.txt
scripts/make_recordings.sh /path/to/nuscenes         # v1.0-mini; checks every file against the catalogue
./replay drop build v0.2.0                           # stamped, optimised build of a tag in a git worktree
./replay run scene-0061                              # or: bazel run //tools/replay -- run scene-0061
```

| command | what it does |
|---|---|
| `replay run <scene\|file\|BUG-id> [--drop] [--window A B] [--preroll] [--set k=v]` | resolve, run, judge, write `runs/<id>/manifest.json` |
| `replay plan ...` | print the resolved plan and the exact command, run nothing |
| `replay rerun runs/<id>` | repeat a run from its manifest and compare both digests |
| `replay bug <BUG-id> [--fix <drop>]` | reproduce on the reported drop (built from the tag or commit if missing), window fidelity, prove the fix |
| `replay ci [--drop] [--junit] [--summary]` | the suite with a verdict; exit code 1 on FAIL |
| `replay golden accept <ci dir> --reason ...` | accept reviewed behaviour as the new baseline |
| `replay drop build <ref> \| list \| import <binary>` | build drops from any git ref, or register a CI artifact |

## How it fits together

```
nuScenes v1.0-mini ──> tools/convert/nuscenes_to_mcap.py ──> recordings (MCAP, JSON messages, sha256-pinned)
                        tools/convert/inject_target.py   ──> must-warn cases (synthetic target, open loop)

recording ──> stack/replay_main (C++17, Bazel) ──> events.jsonl, trace.jsonl, summary.json (digests)
   │            /calib, /ego/state, /radar/front only; /gt/objects never reaches the stack
   └────────> tools/replay/oracle.py: ground truth + the path the car really drove
                                       -> false warnings, missed threats

replay run / bug / ci  = plan (resolve) -> execute -> judge -> manifest / report / JUnit
```

- **Recordings** are MCAP files with JSON messages and a JSON schema, so they open in Foxglove. The converter
  is byte-for-byte deterministic, and `recordings/catalog.json` pins every file by sha256. A changed file is
  refused, never replayed.
- **Drops** are stamped builds (`--config=drop`: `-c opt --stamp`), so every binary reports its version and
  commit. `replay drop build <ref>` builds any tag or commit in a throwaway git worktree. A version resolves to
  the drop of its release tag; if several builds share a version and none is the tag, the tool refuses to guess.
- **The oracle** knows what the stack cannot: the annotated objects and the path the car really drove next.
  A warning with no annotated object in that path at a true TTC below 3.2 s is false. A road user seen by the
  radar in that path at a true TTC below 1.5 s without an active warning is a miss. Objects without radar
  points are counted as not observable, never as misses.
- **Determinism**: the digests cover only what the stack decided (events, per-cycle state at fixed precision),
  never wall-clock timing. CI replays every recording twice.
- **Golden baselines** (`ci/golden/`) record the accepted events per recording, with the reason and the stack
  version that produced them. Known issues can be waived per recording with a ticket; the suite reports when
  a waived bug stops reproducing, so the waiver goes away with the fix.

## Limits, stated plainly

- The stack is a compact radar FCW written for this project, not a production ADAS stack. It runs on x86
  Linux only; nothing here has touched QNX or an in-car target, and x86 timings say nothing about one.
- nuScenes v1.0-mini is 10 drives of about 20 s. That is enough to show the workflow, not to validate an FCW.
  The path-prediction fix of BUG-0003 (yaw rate decaying with a 1 s time constant) was chosen after seeing
  two failures; a larger suite could prove it wrong.
- Replay is open loop: the recorded car never reacts. The injected targets test when the warning fires, not
  braking. Closed-loop resimulation of a changed trajectory is a different problem this project does not solve.
- Off events carry the TTC and range of the current most critical target, not of the warned one, which reads
  oddly in the event log. Left as is; it does not affect the verdicts.
